# TeamRelay 文档协作试点快速上手

## 1. 提交文档需求

在 GitHub Issue 正文或该 Issue 下的新增评论中，以 `/teamrelay` 开头，写清目标文件、期望改动和需要保留的内容。飞书私聊也可使用相同命令。例如：

```text
/teamrelay 请在 README.md 的项目说明末尾补充一句，说明仓库仅包含文档。保留现有英文说明，不修改其他文件。
```

## 2. 等待后台准备修改

项目授权后，TeamRelay 会在后台自动准备 `README.md` 或 `docs/` 下的 Markdown 修改。提交需求后无需保持网页打开。修改准备好不代表草稿 PR 已发布。

## 3. 补充同一任务

- **GitHub：** 在原 Issue 下新增以 `/teamrelay` 开头的评论，例如 `/teamrelay 请把新增说明控制在一句话内。` 系统根据原 Issue 关联同一任务，不需要填写任务编号。
- **飞书私聊：** 使用 `/teamrelay TR-编号 补充内容`，将 `TR-编号` 替换为已有任务的实际编号。要在飞书补充 GitHub 发起的任务，也使用这种方式。

按上述规则提交的补充保留在同一任务中。只有原 PR 仍开放且补充所针对的仓库与原 PR 仓库一致时，才可沿用原 PR。

## 4. 审阅差异并发布草稿 PR

维护者在 **文档任务 → 需要我处理** 中打开任务，逐项审阅实际文件差异，核对改动是否满足需求，以及应保留的内容是否未被改动。确认差异无误后，再发布草稿 PR。草稿 PR 不等于已合并；最终是否合并由有权限的维护者决定。

## 5. 试点边界与异常处理

本试点只处理 README 和 `docs/` 下的 Markdown 文档，不修改源码、不运行 Shell、不自动合并。如果任务失败或无法确定草稿 PR 是否发布，请维护者人工核对任务状态，并到目标仓库确认是否已有对应 PR 及其实际状态，再决定下一步。
