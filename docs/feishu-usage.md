# 通过飞书向机器人提交任务

本仓库用于测试 `dsh-superagent` 的协作流程。你可以通过飞书提交范围明确的小任务，由代理修改仓库并创建 PR（Pull Request，拉取请求），再由人工审阅和合并。

## 1. 准备工作

- 在已配置机器人且关联本仓库的飞书群聊中提交任务，也可以私聊 `dsh-superagent`。
- 群聊和私聊能否接收任务，取决于部署的消息接入、仓库关联和发送者权限配置；不能保证任意群聊或任意账号都能触发任务。
- 本仓库未提供具体的飞书应用配置、可用群聊名单、私聊开通状态或权限名单。无法确认时，请联系维护者核实，不要自行猜测配置值。
- 确保可以在 GitHub 上访问本仓库并查看 PR；合并操作需要相应的仓库权限。

## 2. 提交需求

在群聊输入框中输入 `@`，从飞书弹出的候选列表中**真正选择 `dsh-superagent`**，再输入需求。只键入或粘贴普通文本 `@dsh-superagent` 不等于实际提及机器人，可能不会触发任务。下面示例中的提及也需要通过候选列表选择。

写清楚目标文件、期望结果、需要保留的内容，以及交付方式。例如：

```text
@dsh-superagent 请在 README.md 中增加一段中文项目简介，保留现有英文内容。
只修改文档，完成后创建 PR，并把链接回复到本话题，不要自动合并。
```

私聊时，打开与 `dsh-superagent` 的会话，直接发送需求即可，无需群聊式提及。建议明确仓库，避免目标不清：

```text
请为 dataCodeFarmer/test-dsh-superagent 的 README.md 增加一段中文项目简介，
保留现有英文内容，完成后创建 PR，并在当前会话回复链接。
```

不要在消息、附件或预期提交到 GitHub 的内容中放入密码、访问令牌或私密聊天记录。避免在多个群聊或话题中重复提交同一任务。

## 3. 补充要求、询问进度与停止任务

请在**原任务话题内回复**，私聊则继续在原会话中说明对应任务；同时存在多个任务时，明确任务目标或 PR 链接，避免误指。群聊示例里的 `@dsh-superagent` 同样要从候选列表中选择。

### 补充要求

```text
@dsh-superagent 补充刚才的 README 中文简介任务：请控制在三句话以内，
不要修改现有英文使用说明。
```

如果机器人请求必要信息或访问权限，请在提出问题的原对话中补充。新要求若明显超出原任务范围，应作为独立需求说明。

### 询问进度

```text
@dsh-superagent 请问本话题的 README 中文简介任务现在是什么状态？
是否有需要我补充的信息？
```

任务确认不代表完成；机器人不会为每个内部步骤发送进度通知。可以主动询问，但不要把尚未准备好供审核的 PR 当作最终结果。

### 停止任务

```text
@dsh-superagent 请停止本话题的 README 中文简介任务，不要继续修改，
等我明确确认后再继续。
```

停止任务不等于自动撤销已提交的修改或已合并的内容。若希望恢复，请明确说明继续哪项任务；仅询问状态不等于要求恢复。

## 4. 跨渠道沟通示例

同一任务可能先在 GitHub 提出，再在飞书补充，或先在飞书提出，再到 GitHub 审阅。切换渠道时，请提供**原 Issue 或 PR 的完整链接**，说明这是对哪个任务的补充、询问或反馈，并明确希望关联原任务，避免重复开工。链接有助于定位上下文，但不授予访问权限，也不保证所有部署都已开启跨渠道接入；无法确认时，请维护者核实。

### 从 GitHub 转到飞书补充

在已配置的飞书群聊中真实选择并提及 `dsh-superagent`，或在私聊中省略提及。下面用 `<原 Issue 的完整链接>` 作占位，发送前请替换为实际链接：

```text
@dsh-superagent 关于这个 Issue：<原 Issue 的完整链接>
请关联原任务，补充要求：文档示例也要说明私聊方式，其他要求不变。
请在当前飞书话题回复这次补充的结果。
```

如果原 PR 已合并，应说明这是后续补充，并明确要求新建 PR，不能把已合并的 PR 当作仍可更新的交付：

```text
@dsh-superagent 原任务：<原 Issue 的完整链接>
原 PR：<已合并 PR 的完整链接>
请关联原任务，在现有指南中补充一条询问进度的示例。
原 PR 已合并，请为这次补充创建新的 PR，供人工审阅，并在当前话题回复链接。
```

### 从飞书转到 GitHub 反馈

收到 PR 链接后，直接在该 PR 中留下具体审核意见，不必另开一个内容相同的 Issue。需要明确向代理提出修改请求时，在 GitHub 使用 `@duspring`，不是飞书里的 `@dsh-superagent`。例如在结果 PR 下评论：

```text
@duspring 这是对本 PR 对应文档任务的补充：请在停止任务的示例后，
说明停止不会自动撤销已经合并的修改。其余内容保留，请更新本 PR 供人工审阅。
```

更多 GitHub 操作见[GitHub 使用指南](github-usage.md)。GitHub 可能对外可见，只提供完成修改所需的非敏感需求，不要复制私密飞书消息、附件或凭据；跨渠道沟通不等于授权公开聊天记录。

### 跨渠道询问进度

```text
@dsh-superagent 请查询这个 PR 对应任务的状态：<PR 的完整链接>
请关联原任务，不要重复创建任务或 PR；只需在当前飞书话题说明是否需要我处理。
```

在原渠道发起的任务，结果仍按原话题或会话查看；切换渠道后的新请求请明确回复位置，并在提出该请求的话题查看答复。不要假定所有消息会自动同步到两个渠道，或认为换一个渠道询问就会恢复已明确停止的任务。人工审阅和合并规则不因渠道变化而改变。

## 5. 查看结果并人工审阅

结果会回复到提交任务的**原话题**；私聊任务则回复到原会话。修改准备好供审核后，在那里打开机器人提供的 PR 链接：

1. 阅读 PR 描述，确认修改范围、验证情况和已知限制。
2. 在 **Files changed** 中核对修改是否符合需求，并查看可用的自动化检查结果。
3. 如需调整，在 PR 中留下具体审核意见；如任务受阻，按原对话中的要求提供必要信息或权限。
4. 由人工审阅并决定是否合并，再由有权限的人员在 GitHub 执行合并。机器人不会代替人工批准、合并，也不会启用自动合并。

PR 已创建不代表已经审阅通过或合并；标为 **Draft** 的 PR 仍是未完成的草稿。合并后请确认状态为 **Merged**，并在目标分支查看最终内容。

## 6. 没有收到回应时

先检查群聊中的提及是否是从候选列表选出的真实提及，以及消息是否发到了正确的机器人、群聊或原任务话题。仍无回应时，请维护者确认消息接入、仓库关联、发送者权限及私聊是否可用。本指南不承诺固定响应时间，也不提供未经确认的应用标识、回调地址或权限配置值。
