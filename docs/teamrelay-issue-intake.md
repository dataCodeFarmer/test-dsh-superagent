# TeamRelay GitHub 接单使用说明

本文说明 TeamRelay 当前已实现的 GitHub 接单流程，不沿用其他协作流程中的触发方式或自动回复约定。仓库概况见 [README](../README.md)。本测试仓库仅包含文档，没有需要安装或运行的应用。

## 1. 准备

- 维护者在 TeamRelay 项目设置中启用 **GitHub 接单**，并指定允许账号。
- 发起者必须同时在允许账号名单内、具备目标仓库的写权限；仅能发布 Issue 不代表能够接单。
- 任务范围仅限 `README.md`、`README.<语言>.md` 和 `docs/` 下的 Markdown 文件，不涉及源码、配置或工作流，也不删除文件。
- 当前尚未接入飞书与通用编码任务。具体允许账号请向维护者确认。

## 2. 发起

在目标仓库新建 Issue，**正文开头必须是 `/teamrelay`**，随后写清目标文件、期望结果和限制。例如：

```text
/teamrelay 请新增 docs/writing-guide.md，简要说明文档写作约定。
只新增该 Markdown 文件，保留 README 和现有文档，不修改源码或配置。
```

只有符合允许账号及仓库写权限条件的新 Issue 才会接单。不要在 Issue 中提交密码、访问令牌或私密信息。

接单不等于开始执行：当前不会自动发送接单评论，也不会自动运行模型。不要以是否收到接单评论判断任务状态。

## 3. 续办

需要补充原任务时，在**同一 Issue 新增以 `/teamrelay` 开头的评论**，无需重复新建 Issue。例如：

```text
/teamrelay 补充原任务：请增加一条相对链接写作约定，全文保持简洁，其余限制不变。
```

补充内容归入原任务；继续执行及草稿 PR 更新仍需维护者按下述流程操作，不会因评论而自动运行模型。

## 4. 审阅

1. 维护者在 TeamRelay 网页点击 **开始文档执行**。
2. 执行后审阅实际差异，核对目标文件、内容和限制，确认只涉及许可范围内的 Markdown 文档。
3. 确认差异符合要求后，由维护者批准创建或更新**草稿 PR**；PR 引用原 Issue，便于追溯需求及补充内容。
4. 在 GitHub 中继续检查草稿 PR 的实际改动。草稿 PR 不代表已合并，TeamRelay 当前不会自动合并。

必须先审阅真实差异，再批准发布草稿 PR；接单或开始执行都不等于发布授权。
